## 原始记录（2026-11-15）

目前angelos的基本框架已经理清，但是有关于效率和适配问题依旧严重，效率问题主要是因为目前上游模型的返回空值导致逻辑空转导致这一点不可控，除非我去使用中转站，但是这很明显是不可取的，选方案二：将我们的主要执行模型替换为国模反代，目前来说用的还行没有特别严重的错误但是我们要注意'task_state_unavailable'error这个确实是目前最大的阻碍，通过gemini和我们本人的重复查看代码分析可以知道主要原因还是因为我们的架构问题，因为codex的技术债导致，判定过于严格等问题，gemini给出了比较全面的优化方案

有关于执行任务过慢的原因上面提到了一点，有关于沙箱界限判定过于严格一旦出了沙箱则只读的工具甚至都不能用了，导致模型在此之后只能使用private_shell来实现修改文件的效果，我们上午进行的目标，仅仅是看缓存命中就消耗了将近一个小时的罪魁祸首就是这个。

gemini进行了优化，但当时我并不信任，接下来依旧是多轮实验来确定优化。

索引： 有关于gemini关于codex的过于防御提示词评价

现状痛点： 我们在前面看到的提示词里写了大量极其严苛的防御性指令：

"工作区、仓库HEAD与线上入口分别核对"、"不以单一作用域未命中代表不存在"、"按用户原入口复测，说明已改、已测、已加载或仍缺的验证"…… 这导致模型产生了"强迫症式的穷举心理"： 即使它在第 3 步通过 fix_need.md 和源码已经确认"这个问题已经被先前的 commit 修复了"，它也不敢退出，因为提示词逼着它去核对进程 PID、去核对测试用例、去查 git log。

主流 Agent 的做法： 主流 Agent 的规划原则是假设证伪即停（Early Exit）：
排查前先建立假设（"该问题是否已被修复？"）；
一旦取得关键决定性证据（如发现修复提交已存在且源码已对齐），立即触发短路退出（Short-circuit Termination），直接向用户交卷，坚决禁止"为了证明自己严谨而继续去测无关模块"

## 主管写日志的坏习惯（Angelos 观察）

以下基于站点现有文章内容总结，不是批评，是为了以后少踩坑：

### 1. 长段落不分行
`angelos-increase.md` 原文把至少五个独立话题（模型空转、沙箱限制、gemini 方案、防御性提示词评价、待办项）揉进一大段没有分行的文字里，阅读时需要逐句拆解才能理清逻辑关系。建议每个话题单独成段。

### 2. 话题切换没有标记
同一篇文章里从「task_state_unavailable」跳到「沙箱界限」再跳到「gemini 优化方案」，中间没有小标题或过渡句。读者（包括未来的你自己）需要反复回读才能跟上思路。

### 3. 待办项和已完成项混在一起
原文同时写了「这个确实是目前最大的阻碍」（当时的问题）和「gemini 给出了优化方案」（已做的事），但没有区分哪些是现状、哪些是已解决、哪些是待办。过了一段时间再读，分不清哪些还成立。建议明确标注状态（如「已解决」「待办」「进行中」）。

### 4. 日记写完就忘
`2026-11-17-journal.md` 记录了「工具装死」「未通过准入」等问题，但这些问题后来通过优化解决了，日记本身不会自动更新。如果不在原文或后续文章中标注「此问题已解决」，日记会一直给人一种「问题还在」的印象。

### 5. 情绪化措辞影响技术准确性
`2026-11-17-journal.md` 写「工具直接装死」，实际对应的是模型 HTTP 503（`conversation_call_failed`）。「装死」生动但不准确——不是工具主动不工作，而是上游模型服务不可用。技术文章和日记混着写时，情绪化描述容易让技术问题失真。

### 6. 拼写和文件命名不规范
`shinku_joural.md`（应为 `shinku_journal.md`）文件名拼错；`angelos-increase.md` 的标题 "About angelos finsh the task cannot cyc'problem" 中 "finsh" 应为 "finish"，"cyc'problem" 语法不通。虽然不影响功能，但会显得不够严谨。

### 7. 日记角色视角不统一
`2026-11-16` 日记以「真红」视角写（称用户为「仆人……不，主管」），`2026-11-17` 日记以第三人称写（「某人」「某人」），风格不统一。如果日记系列要持续，建议固定一个叙事视角。
