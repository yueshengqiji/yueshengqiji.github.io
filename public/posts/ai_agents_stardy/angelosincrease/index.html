About angelos finsh the task cannot cyc'problem

1 min read

目前angelos的基本框架已经理清，但是有关于效率和适配问题依旧严重，效率问题主要是因为目前上游模型的返回空值导致逻辑空转导致这一点不可控，除非我去使用中转站，但是这很明显是不可取的，选方案二：将我们的主要执行模型替换为国模反代，目前来说用的还行没有特别严重的错误但是我们要注意’task_state_unavailable’error这个确实是目前最大的阻碍，通过gemini和我们本人的重复查看代码分析可以知道主要原因还是因为我们的架构问题，因为codex的技术债导致，判定过于严格等问题，gemini给出了比较全面的优化方案 有关于执行任务过慢的原因上面提到了一点，接下来我开始完善其他原因，有关于沙箱界限判定过于严格一旦出了沙箱则只读的工具甚至都不能用了，导致模型在此之后只能使用private_shell来实现修改文件的效果，我们上午进行的目标，仅仅是看缓存命中就消耗了将近一个小时的罪魁祸首就是这个，我现在已经 gemini进行了优化，但是很明显我并不信任，接下来依旧是多轮实验来确定优化，这而且就我们现在的使用而言现在task_state_unavailable这个报错还是没有被解决，但愿ai给我改这玩意的时候已经做到了报错精细 索引： 有关于gemini关于codex的过于防御提示词评价 现状痛点： 我们在前面看到的提示词里写了大量极其严苛的防御性指令：

“工作区、仓库HEAD与线上入口分别核对”、“不以单一作用域未命中代表不存在”、“按用户原入口复测，说明已改、已测、已加载或仍缺的验证”…… 这导致模型产生了“强迫症式的穷举心理”： 即使它在第 3 步通过 fix_need.md 和源码已经确认“这个问题已经被先前的 commit 修复了”，它也不敢退出，因为提示词逼着它去核对进程 PID、去核对测试用例、去查 git log。

主流 Agent 的做法： 主流 Agent 的规划原则是假设证伪即停（Early Exit）： 排查前先建立假设（“该问题是否已被修复？”）； 一旦取得关键决定性证据（如发现修复提交已存在且源码已对齐），立即触发短路退出（Short-circuit Termination），直接向用户交卷，坚决禁止“为了证明自己严谨而继续去测无关模块” 现状（代办） 有关于防御性提示词的问题并没有得到解决 我们现在虽然强化了运行速度但是仍然存在边界过重，模型束手束脚的问题
