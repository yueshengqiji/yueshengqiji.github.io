## 一、目的

把「接任务 → 执行 → 验证 → 交付」全过程中最容易返工、最耗时的环节固化为规则，
减少无效动作，缩短任务耗时，而不牺牲必要的取证与验证。

## 二、六条工作方法规则

### 规则 1：先确认入口，再动代码（最高优先）

凡反馈形如「某个东西看不到 / 显示不对 / 只有一项」，动代码前必须先确定：

- 对象是什么：CLI / 网页前端 / 服务接口 / 数据库
- 用什么命令或哪个页面触发
- 实际看到什么

判据：能说出具体入口和实际现象，才算对象明确。说不清就问一句，不猜。

真实代价：把「会话只显示一项」当成浏览器侧栏，改了三个前端文件，整轮作废。

### 规则 2：区分必须重验与可沿用

- 必须重验：决定本轮结论的事实（改完后条数是否 1→15、加载的是不是这个文件）
- 可沿用：背景数字（历史已实测的会话数、工作区数、PID），沿用时标注引自哪一轮实测

判据：这个数字不是本轮结论的依据，就不测。

### 规则 3：验证分两档

- 第一档（必做）：一条命令或一次操作证明核心结论成立
- 第二档（仅异常时）：字节比对、哈希、stderr、逐字段核对

第一档通过且无异常，不做第二档；主管没要求就不主动加。

### 规则 4：命令失败先定位层级

超时、非零退出、工具报错，先说明失败在哪一层（权限 / 网络 / 超时 / 脚本逻辑），
再决定重试还是换法。同一错误不重试第三次。

### 规则 5：写操作前说清三件事

改哪些文件、默认行为会不会变、怎么回滚。事前说，不当事后备注。

真实代价：CLI 改完才提「默认行为变了」。

### 规则 6：写清改动边界

改在按哈希命名的 release 目录、备份目录、临时路径等，动手时就说明，
并评估是否要落到可持久位置（仓库源码 + 固定启动路径），而不是事后补一句备注。

## 三、自检指标（每次任务结束实报，不承诺数字）

| 指标 | 目标 | 说明 |
|---|---|---|
| 返工次数（做完才发现对象错） | 0 | 硬指标 |
| 同一事实跨命令重复验证 | ≤1 次/任务 | 只算背景数字 |
| 验证耗时占比 | 明显低于修改耗时 | 定性判断 |
